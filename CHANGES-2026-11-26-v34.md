## 1. Collision-proof packet markers (the two v32 known limits, closed)

The old scheme wrote each packet file's header as `[Source: <name>]` and
split segments on `/\[Source: ([^\]]+)\]/g`. Two limits followed: a filename
containing `]` was truncated at the first `]` in "from …" attributions, and
`pageOf` counted any `[Page N]` inside a segment — including one a user had
typed literally in a document's body.

The new scheme:

- **Packet token.** Each packet composition gets a token: a djb2 hex hash of
  the ordered entry ids + names. It is deterministic — stable across repeated
  `packetCombinedText()` calls while the composition is unchanged (repeat
  callers compare separately built combined texts), and it changes when the
  composition changes. No per-call randomness.
- **Source header.** On its own line:
  `⟦RTP·SRC·<token>·<entryId>·<encodeURIComponent(name)>⟧`.
  `encodeURIComponent` escapes `]` and every other problematic character, so
  any filename round-trips in full; the decoded name is what displays
  everywhere a name is shown.
- **Page markers.** Our PDF/OCR pipeline inserts genuine page markers only
  as `[Page N] ` at the start of a page chunk. At combine time, exactly
  those anchored markers are translated to `⟦RTP·PG·<token>·N⟧`. Any
  remaining `[Page ` occurrence in a packet body is a user literal and is
  neutralized (`[Page ` → `[ Page `), the same treatment `[Source:` already
  had; body occurrences of `⟦RTP·` are likewise neutralized so body text can
  never forge a marker.
- **Consumers migrated consistently:** `packetCombinedText`, `segmentFor`,
  `pageOf`, `docOf`, `fromPhrase` (packet detection now keys on the new
  header), `findNeedleIndex` (same), `missingTracedFound`, the sentence
  cleaning that strips markers, `buildSourceViewer` (a paragraph that is
  exactly a source header sets the carried source and is never stored as
  body; decoded names shown), and `buildLocIndex`. The whole source was
  grepped for `Source:` / `[Page` patterns; every remaining hit is accounted
  for (the PDF/OCR pipeline's own per-file marker writers, per-file
  `countSourcePages` — left as-is by design, unrelated display copy, and
  deliberate legacy fallbacks in the source viewer for non-packet pasted
  text). Markers never appear in displayed findings, quotes, exports, or
  source-viewer body text.
- **Single-document behavior is unchanged.** The new scheme applies only to
  packet combined text; a single PDF's own `[Page N]` markers resolve
  exactly as in v33 (fixture M4).

## 2. Packet reorder control (review #4's open item, closed)

Each packet item now has Up and Down buttons alongside Remove (disabled at
the ends), handled by the same delegated click listener. On a move:

- The two entries swap in `PACKET`. `FILE_HASHES` slots stay attached to
  their files by pid, and the `FILE_HASHES` array order is updated to match
  the new packet order, so the fingerprint line lists files in the new
  order.
- The packet list re-renders and the combined text rebuilds in the new
  order.
- If a reading built from the old order is on screen, it is cleared the same
  way Remove clears it, with a plain toast that the order changed and to run
  the packet again — **except** the trigger-date state is NOT cleared on
  this path (Remove clears it; reorder must not disturb it, and doesn't).

New fixtures (R-series, all passing): **R1** — two-file packet with an
identical clause in both: first occurrence credits `first.txt` before the
reorder and `second.txt` after moving it up and re-running. **R2** — after
the reorder, `FILE_HASHES` order matches the new packet order by pid and the
fingerprint line lists `second.txt` first. **R3** — a trigger date set
before the reorder is unchanged after it, while the stale reading is cleared
and the paste box holds the new combined text.
